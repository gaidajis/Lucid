## 2024-06-24 - Conditionally Interactive Elements and Keyboard Accessibility
**Learning:** In the Lucid app, many elements like DataCards have dual states: interactive in viewing mode (clickable to view details) and non-interactive in edit mode (where overlaid edit/delete buttons are meant to be interacted with instead). Applying universal `role="button"` and `tabIndex={0}` creates confusing keyboard navigation because screen readers and keyboard users get trapped on or mistakenly interact with the parent container when trying to reach the edit/delete controls.
**Action:** When making dual-state container components keyboard accessible, conditionally apply `role`, `tabIndex`, `onKeyDown`, and interaction styling (like `cursor-pointer`, `hover:shadow`, and `focus-visible`) based on the active mode (e.g., `!editMode`). This ensures keyboard and screen reader users only focus and interact with the intended elements for the current mode, providing a cleaner accessibility tree.
